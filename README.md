# P15 Excel Agent Benchmark 评审材料

这份仓库放的是 P15 前 15 道开发校准题、每道题的 Rubric 和 Evaluator、当前可解释的分数表、图片以及来源记录。它现在用来审查“题目是不是设计对了、评分程序是不是判得公平”，暂时不用来发布系统排名。

## 目前的核心结论

旧评分程序把固定表名、列位、起始行和特定措辞当成了答案的一部分，因此会将业务结果正确的替代布局写成低分或 0 分。旧规则下的 98 份 0 分结果换用 V3 后，84 份变为非零，只有 3 份仍是 0 分。

V3 已经纠正了一批明显误判，也把“业务结果为 0 分”与“评分程序暂时无法判断”分开。它还没有完成 15 道题的公平性审查。订单清洗、原生透视表和 5 道 C 类文档题仍有已知问题；工程选泵、健康数据和销售数据还要加入更多真实布局。

## 建议按这个顺序阅读

1. 先看 [图表及对应数据](outputs/p15_final/FEISHU_ASSET_INDEX.md)，了解旧分数为什么要重审、V3 重评后各题的平均分和实际结果数。
2. 再看 [V3 分数表和口径](results/judge_v3_initial/README.md)，确认 286、322、368 这几个数字分别表示什么。
3. 审查具体规则时，打开 [15 道题的 Rubric 和 Evaluator 导航](docs/EVALUATOR_REVIEW_MAP.md)，再进入每道题的 `rubric.json` 和 `tests/evaluate.py`。
4. 要追题目来源时，看 [公开数据、论文和 Benchmark 设计参考](references/SOURCE_CATALOG.md)。

## 分数应该怎样读

- 每份工作簿的分数为 0 至 1，表示它完成各项业务要求的程度。
- 本轮不使用统一分数线，也不把连续分数转成总体成功率。
- 一道题的 Evaluator 能公平识别合理做法时，平均分越低，说明这道题越能暴露 Agent 的能力缺口。
- 工作簿无法读取、Evaluator 找不到可靠结果区域、题目版本不可比，以及等待 Excel 重算的情况单独记录，不用 0 分代替。

## 当前数据为什么有几个不同的总数

| 数量 | 表示什么 |
|---:|---|
| 360 | 15 道题 × 3 套系统 × 每组 8 次的计划运行数 |
| 351 | 当前批次已经完成并有可用回执的运行数 |
| 368 | 加上历史额外运行和失败重试后，V3 实际检查的 Excel 文件数 |
| 322 | 368 份文件中，V3 目前能给出连续分数的文件数 |
| 286 | 当前计划批次里正常完成、且 V3 已经算出分数的结果数；逐题表和热力图使用这一组 |

368 份文件中另有 46 份暂时没有分数。12 份是 Evaluator 暂时读不懂，24 份来自来源和单位有冲突的旧版政策题，10 份需要 Microsoft Excel 重算。热力图中的 `n` 只统计实际进入平均分的结果，所以会是 5、6、7 或 8。

## V3 Evaluator 的共同思路

1. 先确认答卷对应的题面和输入版本。
2. 按表头、标签、ID 和数值关系查找最终交付，题面明确要求固定结构的情况除外。
3. 检查业务数字、公式关系、记录完整性、来源和对账结果。
4. 只在题面明确要求联动时，修改输入并重新计算。
5. 先记录最早的实质错误，后续数字变化用来说明影响，避免重复扣分。
6. 能可靠判断时给出分数和分项结果；暂时无法判断时，记录具体原因。

每道题的 `rubric.json` 新增了 `review_notes`。它用中文写明这道题检查什么、怎样找答案、接受哪些等价做法、哪些情况应暂时不算分，以及目前还有什么限制。具体代码实现仍在同一题目目录下的 `tests/evaluate.py`。
